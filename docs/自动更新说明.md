## 二、托管侧做了什么

### 1. `publish` 配置（electron-builder.yml）

```yaml
publish:
  provider: github
  owner: wmeng-dev
  repo: Canvas
  releaseType: release
```

- 打包时生成更新元数据：`app-update.yml`（进 `resources/`）+ NSIS 的 `latest.yml`（进输出目录）。
  这两个文件就是"更新载荷"——客户端将来就是靠 `latest.yml` 里的版本号比对来判断要不要更新。
- `--publish always` 时把安装包 + `latest.yml` 传到 GitHub Release。
- **默认不带 `--publish` 就完全不上传**（electron-builder 默认 `publish=never`），所以加这段**不改变**现有本地打包行为。

⚠️ **`releaseType: release` 这行不能删**。electron-builder 对 GitHub 默认发 **draft**，而 electron-updater **会跳过 draft**（表现为"永远提示已是最新"）。想改成人工复核后再发，就删掉这行、发完到网页上手动点 Publish——但别忘了这步。

### 2. 发版工作流（docs/ci/github-actions-release.yml）

打 tag（如 `v0.1.1`）或手动触发 → 构建 Windows / macOS 安装包 → `--publish always` 上传到 GitHub Release。

与已有的 `github-actions-build.yml` 的区别**只在最后一步**：

| 工作流 | 上传到 | 用途 |
|---|---|---|
| `build.yml` | Actions **Artifacts** | 人工下载分发 |
| `release.yml` | GitHub **Release** | 自动更新读这里 |

⚠️ **两个工作流都是"模板"，不是能直接跑的文件**。原因：本机推送用的 PAT 没有 `workflow` 权限，GitHub 会拒绝任何含 `.github/workflows/*` 的推送。启用方式二选一：

1. **GitHub 网页**（推荐，不动 token）：进 **Actions** 页 → 仓库还没有任何 workflow 时，页面是「Get started with GitHub Actions」引导页，点引导语右端的 **「Skip this and set up a workflow yourself →」**（⚠️ 新版 UI **没有** "New workflow" 按钮，别去找它；等仓库里有了 workflow，右上角才会出现「New workflow」）→ 进网页编辑器后把文件名改成 `.github/workflows/release.yml`、内容整段粘贴 `docs/ci/github-actions-release.yml` → 提交。
2. 给 PAT 加上 `workflow` scope，把模板移到 `.github/workflows/release.yml` 再 push。

## 三、发版纪律（接完客户端后必须遵守）

1. **先改 `package.json` 的 `version` 并提交**，再打 tag。
   tag 与包内版本不一致时，客户端会一直认为"已是最新"——因为比对用的是包内版本，不是 tag。
2. tag 用 `v` 前缀（工作流按 `v*` 触发）。
3. 等 Release 变成**已发布**（不是 draft）。
4. macOS 想支持自动更新**必须签名**（见第五节）。

## 四、客户端接入（已完成）

三步都已完成，**第 1 步在本机的坑记录于此备查**。

**最终实现方式（第 1 步）**：不跑 `npm install`，改用**「嵌套装法」**——在一个**空的临时目录**里
`npm install electron-updater`（那次装是干净的、无 package-lock 可对账），再把生成的整棵
`node_modules/` 拷进本项目 `node_modules/electron-updater/node_modules/`。

- 为什么**不拷到顶层**：本项目 `node_modules` 是 pnpm hoisted 布局，直接 `npm install electron-updater`
  会 `removed 83 packages`（**含打包必需的 `app-builder-bin`**、并把 `@types/node` 降级）。嵌套装法**完全绕开顶层**，零副作用。
- 为什么**嵌在 `electron-updater/` 下**：Node 解析从最近的 `node_modules/` 开始找，子进程会先命中嵌套目录，
  **不会**去顶层捡到不兼容版本。
- **核验手法**：对 electron-updater 的依赖逐个 `require.resolve(name, { paths: [<项目>/node_modules/electron-updater] })`，
  确认命中的都是嵌套路径（本次 16 个依赖全部命中）。`package.json` 已声明 `"electron-updater": "^6.8.9"`。

> ⚠️ **别"顺手"在本机跑 `npm install` 或 `npm ci`** —— 会重整整棵树，详见 REFERENCE.md「装依赖」。

### 第 1 步原始记录：为什么不能直接 `npm install` ⚠️

```bash
npm install electron-updater
```

**但这台开发机不能直接跑** —— 实测 `npm install --dry-run electron-updater` 的结果是：

```
added 71 packages, removed 83 packages, and changed 6 packages
```

它会**连带重整整个依赖树**，包括：

- **`remove app-builder-bin`** ← electron-builder 打包必需，删了就没法打包
- `change @types/node 26.6.2 => 20.19.43` ← 把类型定义**降级**
- `remove lodash / rxjs / date-fns / caniuse-lite / ...` 一堆

这正是本项目历史上踩过的"重装依赖后环境坏掉"的坑（症状：`has no exported member 'Node'`、`Cannot find module 'zod/v3/index.cjs'`、`registerTool is not a function`）。

**三种可行做法，任选**：

1. **在另一台干净机器上装**，把 `package.json` + `package-lock.json` 提交回来，本机 `npm ci`（前提是本机能正常 `npm ci`）。
2. **只取这一个包的 tarball**，手工解到 `node_modules/electron-updater` 并补齐其依赖 —— 绕开 npm 的重整，但依赖树要自己核（漏一个只会在"检查更新"时才报错）。
3. **承认本机环境不适合装**：CI 那边 `npm install` 是干净的，直接在 CI 里跑通自动更新链路，本机只做代码开发。

> 注：本机 `npm` **本身是好的**（10.9.7），只是 bash shim 里直接敲 `npm` 会输出乱码。绕过办法是用 node 直接调：
> ```
> node "C:/Users/<你>/.workbuddy/binaries/node/versions/22.22.2-3/node_modules/npm/bin/npm-cli.js" --version
> ```
> 上面那个"会重整依赖树"的结论，就是用这个方式跑 `--dry-run` 得出的，可信。

### 第 2 步：主进程接线（`src/main/auto-update.ts`）

已实现为独立模块 `src/main/auto-update.ts`，导出 `installAutoUpdate(opts)`：

- 在 `src/main/app.ts` 的 `app.whenReady()` 内、`createMainWindow()` 之后调用。
- **只在打包态启用**：`app.isPackaged=false` 直接返回 false（开发态没有 `app-update.yml`，`autoUpdater` 会抛错）。
- `delayMs` 默认 **8s** 再 `checkForUpdates()`，避开开窗 / 装配服务 / 拉 MCP 子进程的 I/O。
- 监听 `update-available` / `update-not-available` / `update-downloaded` / `error`，均写入 `main.log`。
- 策略 `autoDownload=true` + `autoInstallOnAppQuit=true`，**下载完成后**才弹系统原生对话框
  问「立即重启并安装 / 稍后」；选「立即」才 `quitAndInstall(false, true)`。
- 日志复用 `src/main/app.ts` 导出的 `writeMainLog(kind, detail)`。
- ⚠️ **不引 IPC、不进渲染端**（遵守进程边界）。

注意本项目的进程边界约定：**渲染端不发任何网络请求**，所以更新检查和下载都必须在主进程，渲染端只通过 IPC 收"有更新/已就绪"这类状态。别把 `electron-updater` 引进渲染端。

### 第 3 步：配 `GH_TOKEN`（仅手动发布时需要）

CI 里用内置 `GITHUB_TOKEN`（工作流已声明 `permissions: contents: write`）即可。本机手动 `--publish always` 才需要自备 `GH_TOKEN`。**令牌绝不写进仓库/记忆/提交。**

## 五、签名限制（决定自动更新在哪些平台真正可用）

| 平台 | 未签名能否自动更新 | 说明 |
|---|---|---|
| Windows | ✅ 可以 | electron-updater 走 NSIS 安装流程，不强制签名；但用户首次安装会撞 SmartScreen 警告 |
| macOS | ❌ **不行** | Squirrel.Mac 要求包已签名，未签名的更新会被系统拒绝 |

所以**当前（未签名）状态下，自动更新实质上只有 Windows 可用**。要让 macOS 也支持，需要 Apple 开发者证书并在 CI 里配 `CSC_LINK` / `CSC_KEY_PASSWORD`（`docs/ci/github-actions-release.yml` 里有注释说明改哪一行）。

## 六、兜底打包已补 `app-update.yml`（原缺口，已修）

**现象**：在 Windows 上用 `node scripts/dist-win.cjs`（走 rcedit 兜底）打出的安装包，
`resources/` 里**没有** `app-update.yml`（实测确认：全树 + asar 内都没有），自动更新会因此失败。

**根因（读 electron-builder 源码确认，不是猜的）**：兜底流程是
`--dir`（出免安装目录）→ 手工补图标/版本 → `--prepackaged`（压安装包）。
而 `app-update.yml` 是在 `afterPack` 钩子里写的（`app-builder-lib/out/publish/PublishManager.js:88`），
且只在该次构建的目标是 `nsis` / `nsis-*` 时才写（`isSuitableWindowsTarget`）：

- 第 1 步 `--dir` 的目标是 `dir` → 不满足条件 → 不写；
- 第 2 步目标虽是 `nsis`，但 `app-builder-lib/out/platformPackager.js:143` 有一句
  `if (this.packagerOptions.prepackaged != null) return;` —— **`doPack` 直接提前返回，
  `afterPack` 根本不会被调用** → 也不写。

所以兜底流程**必然**缺这个文件。`latest.yml` 不受影响（它由 nsis target 直接产出，**已确认生成**，
在 `installer/latest.yml`）。

**影响范围**：CI（标准流程，非 prepackaged）**不受影响**，能正常产出 `app-update.yml`；
只有**本机兜底流程**打出的安装包不能自动更新。

**已实现**：`scripts/dist-win.cjs` 现在在三条打包路径（`--dir-only` / 标准成功 / `--prepackaged` 之前）
都会调 `ensureAppUpdateYml()` —— 若 `resources/app-update.yml` 缺失，就按 `electron-builder.yml` 的
`publish` 段 + `updaterCacheDirName()`（`sanitize-filename` + `-updater`）动态生成一份，和 rcedit 补资源同属兜底。
内容形如：

```yaml
provider: github
owner: wmeng-dev
repo: Canvas
releaseType: release
updaterCacheDirName: <照抄 CI 产出那份，别手拼>
```

> `updaterCacheDirName` 由 electron-builder 从 `appInfo` 推导（与 `package.json` 的 `name` 相关），
> 写错不会致命，但会留下两套更新缓存目录。**照抄一次 CI 产出的 `app-update.yml` 最稳。**
